# Aero-Piston Engine RUL Prediction System

## AI-Enabled Real-Time Digital Twin — RUL Prediction Module

This module predicts the **Remaining Useful Life (RUL)** of an aero-piston engine using telemetry generated by the Simulink digital twin.

The system uses a **GRU (Gated Recurrent Unit) neural network** because engine degradation is a time-dependent process. Instead of looking at one telemetry reading, the model looks at a sequence of recent telemetry readings and predicts how much useful operating time remains before the engine reaches its defined End-of-Life (EOL) condition.

---

# 1. What Does This System Do?

The overall pipeline is:

```text
Simulink Digital Twin
        |
        | Engine telemetry
        v
+-----------------------------+
| RPM                       |
| FuelFlow                  |
| Torque                    |
| OilTemp                   |
| OilPressure               |
| CHT                       |
| EGT                       |
| Vibration                 |
+-----------------------------+
        |
        v
Preprocessing
(StandardScaler)
        |
        v
50-second rolling sequence
        |
        v
GRU RUL Model
        |
        v
Predicted RUL
        |
        v
RUL in hours
```

Example:

```text
Input:
Last 50 seconds of engine telemetry

Output:
RUL = 5.73 hours
```

This means that, according to the trained model, the engine is estimated to have approximately **5.73 hours of remaining useful operating time** before reaching the EOL condition represented in the training data.

---

# 2. Important Terminology

## Health Index

The system represents engine health using a value between approximately:

```text
1.0 → Healthy
0.7 → Warning region
0.3 → Critical region
0.1 → End of Life
```

The current prototype uses:

```python
HI_warning  = 0.70
HI_critical = 0.30
HI_EOL      = 0.10
```

These are **prototype project thresholds**, not certified aerospace limits.

---

# 3. What Is RUL?

RUL means:

> Remaining Useful Life

It represents the amount of operating time remaining before the engine reaches its defined End-of-Life condition.

Conceptually:

```text
Current Time
     |
     v
     P -------------------------- F
     |                            |
     |       P-F interval         |
     |                            |
     +----------------------------+
                              EOL
```

Where:

* **P** = Point where degradation becomes detectable
* **F** = failure/end-of-life point
* **P-F interval** = time between detectable degradation and failure
* **RUL** = remaining time from the current point until EOL

In this project:

```text
RUL = EOL_time - current_time
```

converted from seconds to hours.

---

# 4. How Is RUL Actually Calculated?

This is extremely important.

The neural network does **not** calculate the training RUL directly from a simple formula.

There are two separate processes:

```text
TRAINING
Simulink → degradation model → Health Index → EOL → RUL label
                                                   |
                                                   v
                                            Train GRU model


LIVE / INFERENCE
Telemetry → GRU model → predicted RUL
```

The first process creates the ground-truth-like labels used to train the neural network.

The second process is what happens when the trained model receives new telemetry.

---

# 5. How Training RUL Is Generated

The training dataset contains simulated engine trajectories.

For each simulation:

1. A fault is selected.
2. Engine operating conditions are randomized.
3. The engine is simulated.
4. Degradation increases over time.
5. Fault severity increases.
6. Damage rate is calculated.
7. Damage accumulates.
8. Health Index decreases.
9. EOL is detected.
10. RUL is calculated for every timestamp.

---

The current dataset uses four fault types:

```text
FaultID 0 = Healthy
FaultID 1 = Misfire
FaultID 2 = Overheating
FaultID 3 = Oil-pressure failure
FaultID 4 = Fuel starvation
```

The RUL training dataset currently contains:

```text
Fault 1 → 5 runs
Fault 2 → 5 runs
Fault 3 → 5 runs
Fault 4 → 5 runs
```

Total:

```text
20 independent simulated trajectories
```

The healthy trajectory is not included in the final RUL training dataset because it does not reach the defined EOL condition during the required simulation period.

# 7. Operating Conditions

Each simulation randomly varies operating conditions.

Examples include:

```text
Throttle
Engine Load
Altitude
Ambient Temperature
```

The purpose is to prevent the neural network from simply memorizing one fixed engine trajectory.

For example, two Fault 1 simulations may have different:

```text
Throttle
Altitude
Ambient temperature
Engine load
Degradation duration
```

while still representing the same general fault.

This creates different trajectories for the model to learn from.

---

# 8. Degradation Model

The degradation system uses a Health Index.

Initially:

```text
Health Index = 1.0
```

As damage accumulates:

```text
Health Index decreases
```

The simplified relationship is:

```text
HealthIndex = 1 - accumulated_damage
```

The prototype defines:

```text
HI_EOL = 0.10
```

Therefore EOL occurs when:

```text
HealthIndex <= 0.10
```

---

# 9. Operating Severity

Engine operating conditions contribute to degradation.

The system calculates an:

```text
OperatingSeverity
```

using:

```text
RPM
Load
Thermal condition
```

The current weights are:

```text
RPM contribution      = 30%
Load contribution     = 30%
Thermal contribution  = 40%
```

Therefore:

```text
OperatingSeverity =
    0.30 × RPM_severity
  + 0.30 × Load_severity
  + 0.40 × Thermal_severity
```

This produces a value representing how stressful the current operating condition is.

---

# 10. Fault Severity

Fault severity increases with degradation time.

For the training dataset:

```python
FaultSeverity = min(time / degradation_duration, 1)
```

Therefore:

```text
At beginning:
FaultSeverity ≈ 0

During degradation:
FaultSeverity increases

At degradation duration:
FaultSeverity = 1
```

Example:

If:

```text
degradation_duration = 30,000 seconds
```

then at:

```text
time = 15,000 seconds
```

we get:

```text
FaultSeverity = 15000 / 30000
               = 0.5
```

---

# 11. Fault Severity Multiplier

Fault severity affects the damage rate.

The current prototype uses:

```text
Fault severity < 0.30
        ↓
Multiplier = 1.0

0.30 – 0.60
        ↓
Multiplier = 1.5

0.60 – 0.80
        ↓
Multiplier = 3.0

>= 0.80
        ↓
Multiplier = 6.0
```

These values are prototype tuning parameters.

They are not certified aerospace engineering limits.

---

# 12. Damage Rate

The system combines operating severity, fault severity and the base damage rate.

Conceptually:

```text
Damage Rate
    =
Base Damage Rate
× Operating Severity Effect
× Fault Severity Multiplier
```

The current base damage rate is:

```python
base_damage_rate = 1e-5
```

The exact implementation used by the dataset generator should be treated as the source of truth for the labels.

---

# 13. Accumulated Damage

Damage accumulates over time.

Conceptually:

```text
Damage(t)
=
Damage(t-1)
+
DamageRate(t) × Δt
```

As damage increases:

```text
Health Index decreases
```

For the prototype:

```text
HealthIndex = 1 - accumulated_damage
```

with the EOL threshold:

```text
HealthIndex <= 0.10
```

---

# 14. Finding EOL

For every simulated run, the system searches for the **first timestamp** where:

```python
HealthIndex <= HI_EOL
```

with:

```python
HI_EOL = 0.10
```

Suppose:

```text
EOL time = 25,000 seconds
```

Then:

```text
EOL = 25,000 seconds
```

---

# 15. Calculating the RUL Label

Once EOL is known, every row in that trajectory gets an RUL value.

The formula is:

```text
RUL_seconds = EOL_time - current_time
```

Then:

```text
RUL_hours = RUL_seconds / 3600
```

Example:

```text
EOL time = 25,000 seconds
Current time = 10,000 seconds

RUL = 25,000 - 10,000
    = 15,000 seconds

RUL_hours = 15,000 / 3600
          = 4.1667 hours
```

Therefore the training label for that row is:

```text
RUL_hours = 4.1667
```

At EOL:

```text
RUL = 0
```

---

# 16. Very Important: The GRU Does Not Use EOL Time During Inference

During training, we know the future because the entire simulated trajectory is available.

Therefore we can calculate:

```text
EOL_time
```

and create:

```text
RUL_hours
```

as the training target.

During real-time operation, however, we obviously don't know when the engine will fail.

Therefore:

```text
LIVE TELEMETRY
      ↓
GRU
      ↓
Predicted RUL
```

The GRU learns the relationship between the **current/recent engine behavior** and the RUL values generated during training.

It estimates RUL without being given the future EOL time.

# 19. Why 50 Samples?

The final RUL dataset is saved at:

```text
1 sample / second
```

Therefore:

```text
50 samples = 50 seconds
```

The model looks at approximately the **last 50 seconds of engine behavior**.

For example:

```text
t = 1000 sec
t = 1001 sec
t = 1002 sec
...
t = 1049 sec
```

These 50 samples are provided to the GRU.

The model predicts RUL corresponding to the final point:

```text
t = 1049 sec
```

---

# 20. Why Not Give the Model One Row?

A single row might look like:

```text
RPM = 3500
FuelFlow = 0.18
Torque = 7.2
OilTemp = 92
OilPressure = 4.3
CHT = 110
EGT = 600
Vibration = 0.12
```

That tells us the current engine state.

But it doesn't tell us whether the engine is:

```text
Stable
```

or:

```text
Slowly degrading
```

For example:

```text
OilTemp:
85 → 86 → 87 → 88 → 89 → 90
```

is very different from:

```text
OilTemp:
90 → 90 → 89 → 90 → 89 → 90
```

even if the final value is similar.

A recurrent neural network can use the **trend over time**.

That is why a GRU is used.

---

# 21. Why GRU?

GRU stands for:

> Gated Recurrent Unit

It is designed for sequential/time-series data.

Engine telemetry is naturally sequential:

```text
Time
 ↓
RPM(t)
RPM(t+1)
RPM(t+2)
...
```

The GRU maintains an internal representation of the recent history.

Instead of learning:

```text
Telemetry → RUL
```

it learns approximately:

```text
Telemetry history → degradation pattern → RUL
```

This is much more appropriate for a degradation prediction problem.

# 22. Model Architecture

The trained model is:

```text
GRURULRegressor(
  GRU(8, 96, num_layers=2)
  LayerNorm(96)
  Linear(96 → 64)
  GELU
  Dropout(0.15)
  Linear(64 → 1)
  Softplus
)
```

Detailed architecture:

```text
Input
50 × 8
   |
   v
GRU
Input size = 8
Hidden size = 96
Layers = 2
Dropout = 0.15
   |
   v
Last timestep
96 values
   |
   v
LayerNorm
96
   |
   v
Linear
96 → 64
   |
   v
GELU
   |
   v
Dropout
0.15
   |
   v
Linear
64 → 1
   |
   v
Softplus
   |
   v
RUL
```

---

# 23. Why 96 GRU Hidden Units?

The GRU needs an internal representation of the engine's temporal behavior.

The value:

```text
hidden_size = 96
```

means the GRU maintains a 96-dimensional hidden representation.

This is a model-capacity choice.

It is large enough to represent relationships between the eight telemetry signals while remaining small enough for practical training on the current dataset.

---

# 24. Why 2 GRU Layers?

The first GRU layer can learn lower-level temporal patterns.

For example:

```text
temperature trends
RPM changes
vibration changes
```

The second layer can combine those representations into more complex degradation patterns.

So:

```text
Telemetry
   ↓
GRU layer 1
   ↓
Temporal representation
   ↓
GRU layer 2
   ↓
Higher-level degradation representation
```

---

# 25. Why LayerNorm?

After taking the final GRU representation:

```python
x = output[:, -1, :]
```

the model applies:

```python
LayerNorm(96)
```

Layer normalization helps stabilize the representation passed into the fully connected layers.

---

# 26. Why GELU?

The fully connected section uses:

```python
GELU()
```

as the nonlinear activation.

This allows the model to learn nonlinear relationships between the GRU representation and RUL.

---

# 27. Why Softplus?

The final layer is:

```python
Linear(64 → 1)
```

followed by:

```python
Softplus()
```

Softplus produces a positive output.

Therefore the model naturally represents:

```text
RUL >= 0
```

This is useful because a negative RUL does not make physical sense for the intended prediction.

# 33. Train / Validation / Test Split

The data is split by **RunID**, not randomly by individual rows.

This is very important.

We have:

```text
20 independent simulation runs
```

The model uses:

```text
12 runs → Training
4 runs  → Validation
4 runs  → Testing
```

Therefore the same trajectory is not supposed to appear in both training and testing.

This prevents severe data leakage.

---

# 34. Why Split by Run?

Suppose we randomly split individual rows.

You could have:

```text
Run 1, seconds 1000–1050 → Training

Run 1, seconds 1051–1100 → Testing
```

Those sequences are extremely similar.

The model could appear extremely accurate simply because it has already seen nearly the same trajectory.

Instead:

```text
Run 1 → Train
Run 2 → Train
...
Run 18 → Test
Run 19 → Test
```

The model must generalize to an entire trajectory it did not train on.

That is a much more meaningful test.

---

# 35. StandardScaler

Before entering the GRU, the eight features are standardized.

Conceptually:

```text
x_scaled = (x - mean) / standard_deviation
```

For example:

```text
RPM
```

might have values in the thousands, while:

```text
Vibration
```

may have values near zero.

Without scaling, the larger numerical features can dominate optimization.

---

# 36. Important: How the Scaler Is Trained

The scaler is fitted **only on the training runs**.

```text
Training data
      ↓
Fit StandardScaler
      ↓
rul_scaler.pkl
```

Then the same scaler is applied to:

```text
Training data
Validation data
Test data
Live data
```

We do NOT fit a separate scaler to validation/test/live data.

This prevents information leakage.

Because engine telemetry is continuous.


This teaches the model how RUL changes continuously.

# 40. Why Huber Loss?

RUL regression can occasionally have large prediction errors.

Mean Squared Error heavily penalizes large errors.

Huber Loss behaves more gently for large errors while still encouraging accurate predictions.

This makes it a reasonable choice for the current prototype.

# 44. Real-Time Operation

During real-time operation, we maintain a rolling buffer.

For example:

```text
Incoming sample 1
Incoming sample 2
Incoming sample 3
...
Incoming sample 50
```

Once 50 samples are available:

```text
[50 × 8]
     ↓
Scaler
     ↓
GRU
     ↓
RUL
```

When the next sample arrives:

```text
Remove oldest sample
Add newest sample
```

so the window becomes:

```text
samples 2–51
```

Then the model predicts again.

```text
(256, 50, 8)
```

During training the batch size is:

```text
256
```

but during live inference we can use:

```text
batch = 1
```

# 53. Live Inference Process

Conceptually:

```python
window = []

while True:

    sample = get_new_telemetry()

    window.append(sample)

    if len(window) >= 50:

        window = window[-50:]

        scaled = scaler.transform(window)

        x = torch.tensor(
            scaled,
            dtype=torch.float32
        )

        x = x.unsqueeze(0)

        with torch.no_grad():
            rul = model(x)

        print("RUL:", rul.item(), "hours")
```

The actual telemetry source can later be:

```text
Simulink
MQTT
REST API
WebSocket
Serial
Flight computer
```

depending on the final architecture.

# 54. Why the Model Needs the Scaler During Inference

The model was trained using scaled data.

Therefore live data must use the **same scaler**.

Incorrect:

```text
Raw telemetry
      ↓
GRU
```

Correct:

```text
Raw telemetry
      ↓
rul_scaler.pkl
      ↓
Scaled telemetry
      ↓
GRU
      ↓
RUL
```

Never fit a new scaler on live data.

# 55. What Happens If We Change the Input Order?

This is extremely important.

The model expects:

```text
[RPM,
 FuelFlow,
 Torque,
 OilTemp,
 OilPressure,
 CHT,
 EGT,
 Vibration]
```

If you accidentally provide:

```text
[FuelFlow,
 RPM,
 Torque,
 OilTemp,
 ...]
```

the model will receive completely incorrect feature meanings.

The prediction can become meaningless.

Therefore the feature order must remain identical during:

```text
Training
Validation
Testing
Inference
```

# 56. Current Dataset Sampling

The Simulink engine itself runs with:

```text
simulation timestep ≈ 0.1 seconds
```

However, the final RUL dataset is saved at:

```text
1 second intervals
```

Therefore the RUL model sees:

```text
1 sample / second
```

and:

```text
50 samples = 50 seconds
```

This was done to reduce dataset size and make the RUL model easier to train.

---

# 57. Why Not Use the 0.1 Second Data Directly?

If we used:

```text
0.1 sec/sample
```

then:

```text
50 samples = 5 seconds
```

The dataset would also contain approximately ten times more rows.

For the current prototype, 1-second sampling provides a simpler training setup while still preserving useful degradation trends.

---

# 58. Important Limitation: Synthetic RUL Labels

This is the most important limitation of the current system.

The RUL labels are generated from the project's simulated degradation model.

They are not obtained from:

```text
Real UAV engine failures
```

or:

```text
Real engine maintenance records
```

Therefore the trained model currently learns:

```text
Simulated telemetry
        ↓
Simulated degradation behavior
        ↓
Simulated RUL
```

It has not been demonstrated that the model predicts the actual physical lifetime of a real aero-piston engine.

---

# 59. What Can We Claim?

A technically accurate project claim is:

> "A GRU-based temporal regression model was trained on simulated aero-piston engine degradation trajectories to estimate remaining useful life from multivariate engine telemetry."

The current evaluation can be stated as:

> "On held-out simulated trajectories, the model achieved a test MAE of 0.3155 hours."

Avoid claiming:

> "The system predicts real engine failure with 19-minute accuracy."

That would require real-world validation data.

---

# 60. Why 20 Runs Are Not the Same as 464,566 Independent Samples

The dataset contains:

```text
464,566 rows
```

but only:

```text
20 independent trajectories
```

This distinction matters.

Many rows come from the same continuous simulation.

Therefore the real diversity of the training data is closer to:

```text
20 independent engine trajectories
```

rather than:

```text
464,566 independent experiments
```

The run-based train/test split is therefore essential.

# 68. Final Concept

The most important idea to remember is:

```text
We don't tell the AI:
"RUL = EOL - current time"
during inference.

Instead:

During training:
Telemetry history
       +
Known simulated future
       ↓
RUL label
       ↓
GRU learns the relationship


During deployment:
Telemetry history
       ↓
GRU
       ↓
Predicted RUL
```

So the **formula creates the training target**, while the **GRU learns to estimate that target from telemetry alone**.

That is the fundamental purpose of this RUL module.
